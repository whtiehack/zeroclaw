# 2026-03-19 上游提单失误记录

更新时间：`2026-03-19`

## 1. 背景

在一次以上游 `master` 为 base 的缺陷提报中，我为 native tool call 的 draft 文本丢失问题创建了：

- issue `#3974`
- PR `#3976`

提报目标本身是对的，但在上游沟通内容里犯了两类不该犯的错误。

## 2. 错误一：把 `master_wecom` 分支私有语境带进了上游

错误表现：

- 在上游 issue / PR 里使用了 `wecom_ws` 作为主要问题描述对象。

为什么这是错误：

- `wecom_ws` 是 `master_wecom` 分支特有语境，不是上游通用 channel 概念。
- 上游问题描述应该优先使用上游已有、可复现、可验证的对象。
- 对这次问题来说，更合适的上游描述对象是 `telegram`，因为它本身支持 draft updates，且当前回归测试也是按 `telegram` 路径验证的。

正确做法：

- 上游 issue / PR 默认使用上游已有实现来描述问题。
- 如果问题根因在公共层，优先写“公共行为 + 上游现成 channel 示例”，不要把 `master_wecom` 专属名词带进去。

## 3. 错误二：issue 示例里暴露了本地隐私信息

错误表现：

- 在 issue `Logs / stack traces` 示例中，带入了带有本地主机名、脚本路径、命令细节的真实样例。

为什么这是错误：

- 上游 issue 不应该暴露本地环境信息。
- 即便这些内容不是密钥，也会泄露个人工作流、主机命名、目录布局和运维脚本路径。
- 这类信息对上游定位公共问题没有必要。

正确做法：

- 日志、命令、工具调用示例一律改写成中性占位内容。
- 优先使用通用名字，例如 `count_tool`、`example.com`、`/path/to/script`，不要直接贴本地真实值。

## 4. 已做修正

- 已将 issue `#3974` 中的日志示例替换为中性占位内容。
- 已将 issue `#3974` 的复现语境改写为 `telegram`。
- 已将 PR `#3976` 中对 `wecom_ws` 的描述改写为 `telegram`。

## 5. 后续约束

后续凡是从 `master_wecom` 向上游提 issue / PR，先做下面的最小检查：

- 检查描述对象是否是上游已有概念，而不是 `master_wecom` 私有命名。
- 检查所有日志、命令、路径、主机名是否已经脱敏。
- 检查示例是否能被上游维护者在不依赖本地分支的前提下理解。
- 如果根因在公共层，优先用上游现成 channel 或 provider 举例。

## 6. 本次教训

- `master_wecom` 的默认开发语境不能直接外推到上游。
- “问题本身判断正确”不等于“上游表达合格”。
- 上游沟通材料必须先过一遍“公共性”和“脱敏”检查，再提交。
